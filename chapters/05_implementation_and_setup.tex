\chapter{Implementation and Test Setup}\label{chap:implementation}

This chapter realises the benchmarking design of \cref{chap:methodology} as a concrete, reproducible deployment. Three connector implementations run on a single dedicated benchmark host. Each is deployed twice, as an identity-enabled arm for goal $G_1$ and an identity-disabled arm for goal $G_2$. The two arms are identical in every layer except the identity stack. A shared observability pipeline instruments every runtime with the same agent, and a single k6 load driver, byte-identical across all connector repositories, generates the workloads. \Cref{sec:sut,sec:test-env} name the systems under test and the substrate they run on, and \cref{sec:deployment,sec:data-tools} detail the two deployment arms and the observability stack. \Cref{sec:workload-gen,sec:data-analysis} describe the load generator and the reduction of the archived measurements, and \cref{sec:reproducibility} states what a replication of this work requires.


\section{Systems Under Test}\label{sec:sut}

Of the four connector implementations introduced in \cref{subsec:different-connectors}, three are realised in the experimental setup: the Factory-X \gls{edc}, the Fraunhofer ISST \gls{edc}, and DSP-Native BaSyx. Tractus-X \gls{edc} could not be brought to instrumentation parity with the other three within the time frame of this work and is therefore excluded from the deployed setup; the comparison in the remainder of the thesis covers the three instrumented implementations.

The three systems divide into two deployment shapes. The Factory-X and Fraunhofer ISST deployments are symmetric two-participant dataspaces: a consumer and a provider, each consisting of an \gls{edc} control plane and data plane, exchange catalog, negotiation, and transfer messages over the \gls{dsp}~\citep{datapsaceProtocol2025}. DSP-Native BaSyx is asymmetric by construction. Its provider is a single Spring Boot application that embeds the \gls{aas} repository and speaks \gls{dsp} natively, so control plane and data plane collapse into one process. The data transfer is then a synchronous request against the \gls{aas} \gls{api}~\citep{dspNativeBasyx}. Its consumer side, in the identity-enabled arm, is a Factory-X \gls{edc} control plane. This structural asymmetry is not a defect of the setup but a property of the system under test, and it becomes explanatory input for the architectural interpretation reported in \cref{sec:x1-overhead}.

Two consequences of this environment shape the experiment design. First, all services of one deployment share this single host: both participants, their databases, the monitoring stack, and the load driver. The host can therefore saturate before the connector does. The host-level exporter of \cref{subsec:host-metrics} exists to make that ceiling visible, so that it cannot masquerade as a connector limit. Second, the connectors share the host and the monitoring backend, so they are measured strictly one at a time. This is the design commitment stated in \cref{sec:research-methodology}: two connector deployments never run concurrently, and nothing else is scheduled on the machine during a measurement window.

\subsection{Software Substrate}\label{subsec:substrate}

Every deployment arm is a single Docker Compose file, checked into the respective connector repository, that describes the complete stack: connector runtimes, identity infrastructure, databases, secret store, and monitoring~\citep{dockerComposeDocs}. Docker Compose on one host is a deliberate choice over a Kubernetes cluster. The benchmark is single-host by design (\cref{subsec:hardware}), so an orchestrator would add a scheduling layer whose placement and restart decisions vary between runs, without adding any capability the experiment needs. With Compose, service co-location is deterministic and one YAML file per arm carries the entire deployment topology. This auditability carries the fairness argument of \cref{sec:comparing-benchmarks} directly into the artefacts: verifying that two arms differ only in the identity layer reduces to diffing two version-controlled Compose files.

Resource discipline is enforced uniformly at two levels. At the container level, every service carries an explicit Compose memory limit -- 768\,MB for control planes and data planes, 512\,MB for identity services and infrastructure. At the process level, every \gls{jvm} is started with fixed heap bounds via \texttt{JAVA\_TOOL\_OPTIONS}: \texttt{-Xms512m -Xmx768m} for control and data planes and \texttt{-Xms256m -Xmx512m} for identity services, identical across connectors and across arms. Both limits are part of the Compose files and therefore of the audited configuration.

\section{Deployment Architecture}\label{sec:deployment}

The central structural property of the setup is deployment parity. For each connector, the identity-enabled arm ($G_1$) and the identity-disabled arm ($G_2$) share the same host, the same resource limits, the same databases and secret store, the same monitoring stack, the same seeded dataset, and the same driver. The identity layer is the only permitted difference. Parity licenses reading the per-connector difference $G_1 - G_2$ as the identity overhead X1, and not as an artefact of two divergent deployments (\cref{sec:gqm-decomposition}). It operationalises the factor-control requirement of \emph{The Art of Computer Systems Performance Analysis} and the fairness attribute of the benchmarking standard~\citep{jain1991art, Ralph2020}. \Cref{fig:identity-onoff-parity} depicts the principle and the per-connector mechanism.

\subsection{Identity-Enabled Arm (G1): MVD-Based Deployments}\label{subsec:mvd}

The identity-enabled arm of each connector is a \gls{mvd}: the smallest deployment in which the full \gls{dcp} trust chain runs end to end~\citep{eclipseEdcIdentityHub}. Beyond the two participants, it comprises an issuer service, which issues the membership credential that the dataspace requires, and one Identity Hub per participant, which stores the participant's \glspl{vc} and answers presentation queries. Every \gls{dsp} exchange then carries the full cryptographic cost of \gls{dcp}. The requesting connector obtains a self-issued token from its \gls{sts}. The receiving connector resolves the counterparty's \gls{did} document, queries the presented \gls{vp}, and verifies credential signatures before it admits the request~\citep{dcpSpec}.

The identity infrastructure ships empty, so the dataspace needs provisioning once per deployment before any transfer can succeed. A provisioning script registers the issuer as trusted, creates both participants in their Identity Hubs, requests and stores their membership credentials, and writes the \gls{sts} client secrets to Vault. That script is fully automated (\cref{subsec:k6-harness}) and belongs to the deployment procedure, not to the measured window.

Concretely, each arm runs the following services:

\begin{itemize}[leftmargin=*, itemsep=2pt, topsep=4pt]
    \item \textbf{Fraunhofer ISST.} The \gls{dcp} control-plane and federated-catalog assemblies, two Identity Hubs, the issuer service, and an nginx instance serving the static \texttt{did:web} documents.
    \item \textbf{Factory-X.} Its issuer service and two Identity Hubs, next to the two control planes and two data planes.
    \item \textbf{BaSyx.} The same Factory-X identity infrastructure, an \gls{edc} consumer control plane, and the BaSyx provider configured with its \gls{dcp}-backed validation service (\texttt{validationservice=mvd}). That service verifies \gls{jwt} signatures, resolves \glspl{did}, and queries the membership \gls{vp} for every incoming \gls{dsp} request.
\end{itemize}

\subsection{Identity-Disabled Arm (G2): Mock Identity}\label{subsec:mock-arm}

In the identity-disabled arm, verification is short-circuited rather than removed: a mock identity service still issues and accepts a token, but no signature verification, \gls{did} resolution, or credential-service round trip takes place (\cref{sec:gqm-decomposition}). The issuer and the Identity Hubs are absent from these deployments entirely. Because the three connectors wire identity into their stacks differently, the mechanism that disables it necessarily differs per connector; the three mechanisms are described here and their heterogeneity is carried as an explicit construct-validity caveat into \cref{chap:results-evaluation}.

\textbf{Fraunhofer ISST \gls{edc}: runtime swap.} The upstream base control plane bundles the stock \texttt{org.eclipse.edc:iam-mock} extension, and the \gls{dcp} assembly explicitly excludes it in favour of the real identity stack. The identity-disabled arm therefore requires no code at all: the Compose file substitutes \texttt{controlplane-persistence} (and the matching federated-catalog assembly) for the \texttt{-dcp} variants. One pitfall is deliberately avoided: the repository's stock \texttt{iam-mock} Compose file runs in-memory stores and no monitoring, so using it as the $G_2$ arm would change persistence and observability along with identity and confound the comparison. The benchmark's $G_2$ Compose file instead replicates the $G_1$ topology -- PostgreSQL, Vault, and the full monitoring stack -- and swaps only the two runtime images.

\textbf{Factory-X \gls{edc}: benchmark-specific mock extension.} Factory-X compiles its \gls{dcp} integration into the control-plane distribution, and its transfer path expects an \gls{sts} to be present, so neither removing the identity modules nor substituting the stock \texttt{iam-mock} produces a bootable runtime. This work therefore adds a small extension, \texttt{fx-mock-identity}, that supplies the missing services in process. The first is a \texttt{MockVcIdentityService} implementing the \gls{edc} \texttt{IdentityService} interface. It embeds a membership credential into every outgoing token and verifies incoming tokens by parsing them back, with no signature check, no \gls{did} resolution, and no credential-service query. The second is a local \gls{sts}, so that the transfer path finds the token service it expects. The extension is packaged as the sole identity provider into a dedicated control-plane assembly, \texttt{edc-controlplane-\allowbreak postgresql-\allowbreak hashicorp-\allowbreak vault-\allowbreak fxmock}, and the $G_2$ Compose file differs from $G_1$ only in using that image and omitting the identity infrastructure. The data plane runs the same image in both arms, its token-refresh settings pointing at an unused placeholder in the identity-disabled arm. Identity work could therefore still remain on the data path. The payload sweep (\cref{subsec:scenarios}) checks that risk empirically, and \cref{chap:results-evaluation} discusses the result.

\textbf{DSP-Native BaSyx: validation-service switch.} The embedded \texttt{dataspace-\allowbreak protocol-\allowbreak lib} selects its token validator by configuration~\citep{dspProtocolLib}: the $G_2$ arm sets the library property \texttt{org.factoryx.\allowbreak library.\allowbreak validationservice} to \texttt{mock}, selecting a \texttt{MockValidationService} that accepts a plain JSON token of the form \texttt{\{clientId, audience\}} without any cryptographic processing. The provider process is otherwise identical to the $G_1$ arm, including the patched image and the MongoDB, Keycloak, and MQTT internals. The mock token format is, however, wire-incompatible with the \gls{dcp} tokens that an \gls{edc} consumer emits, so the \gls{edc} consumer control plane cannot drive this arm. The $G_2$ deployment therefore replaces it with a raw-\gls{dsp} driver -- the k6 client speaks the \gls{dsp} \gls{api} of the provider directly, and a lightweight callback sink receives the asynchronous \gls{dsp} callbacks that a control plane would normally consume. The consumer side of the BaSyx pair thus differs between the arms as well as the provider side; consequences for interpreting the BaSyx X1 delta are treated in \cref{chap:results-evaluation}.

\subsection{Deployment Parity and Per-Connector Topology}\label{subsec:parity}

\Cref{tab:arm-topology} summarises the per-connector service topology of both arms. Within each connector pair, the held-constant set comprises:

\begin{itemize}[leftmargin=*, itemsep=1pt, topsep=4pt]
    \item the host and its configuration;
    \item the container memory limits and \gls{jvm} heap bounds;
    \item the persistence and secret-store services;
    \item the complete observability stack;
    \item the seeded asset and policy;
    \item the transfer type (\texttt{HttpData-PULL});
    \item the poll interval of the driver;
    \item the application log level, and the driver code itself.
\end{itemize}

The varied set is exactly the identity layer, plus the consumer-side driver discussed above for BaSyx.

The log level is held constant for a reason that is not obvious and that measurement reveals. At its default level the BaSyx provider emits a log record per request, and its \gls{mvd} validation component records the full inbound \gls{jwt} on every one -- roughly 1.5\,kB per line, and 1.46 million lines over a single saturation run. That component exists only in the identity-enabled arm. That arm therefore wrote about seven times as much log per transaction as the identity-disabled one, which put string formatting and log I/O on the request path of one arm but not the other. Left alone it would have been counted as identity overhead. Both BaSyx arms therefore run with the application packages at \texttt{WARN} and the root logger at \texttt{INFO}, which removes the asymmetry while retaining start-up and error records for post-hoc diagnosis. No such adjustment is required for the \gls{edc} connectors, whose control planes do not log per request at their configured levels.

\section{Observability Stack}\label{sec:data-tools}

\Cref{sec:metrics} requires two independent vantage points: the client view of the load generator and the server view of the systems under test. The server view is realised by one pipeline -- \gls{otel} instrumentation feeding Prometheus for metrics and Tempo for traces, with Grafana as the reading instrument -- deployed with byte-identical configuration in all three connector repositories.

\textbf{Why this composition.} The pipeline has three layers because \gls{otel} deliberately covers only the first of them. Instrumentation has to be identical across heterogeneous runtimes, because an instrument that varies per connector reintroduces the very confound the fairness requirement forbids~\citep{Ralph2020}. \Gls{otel} meets that condition as a vendor- and tool-agnostic \gls{cncf} standard. It is explicitly not an observability backend, and leaves storage and visualisation to other tools~\citep{otelWhatIs}. That boundary forces an explicit backend decision. Prometheus answers it on the three properties this benchmark depends on:

\begin{itemize}[leftmargin=*, itemsep=2pt, topsep=4pt]
    \item a dimensional data model queried through PromQL, which yields the per-service breakdown the analysis needs~\citep{prometheusOverview};
    \item counter and histogram types that match the rate-error-duration view~\citep{prometheusMetricTypes};
    \item a range-query endpoint that evaluates an expression between an explicit start and end timestamp, which makes the time-aligned per-run snapshot of \cref{subsec:orchestration} possible~\citep{prometheusHttpApi}.
\end{itemize}
 Grafana supplies the frontend that \gls{otel} leaves open, over the metric and the trace store alike~\citep{grafanaDocs, grafanaTempoDocs}. Two alternatives are rejected on the same criteria: a hosted commercial observability service would move telemetry off the benchmark host and forfeit reproduction from pinned open images~\citep{papadopoulos2021reproducible}, and consuming each connector's own metrics endpoint would make the instrument a per-connector variable. Instrumenting at all has a cost, and this work does not assume it away: monitoring frameworks impose measurable overhead on the application they observe~\citep{reichelt2021overhead}. The agent is therefore itself put through the on-versus-off comparison of \cref{subsec:tracing}.

\subsection{Metrics Pipeline: OpenTelemetry, Prometheus, and Grafana}\label{subsec:metrics-pipeline}

\textbf{Instrumentation.} The \gls{otel} Java agent (version 2.8.0) instruments every connector \gls{jvm}, attached at start-up via the \texttt{-javaagent} flag. It injects bytecode at class-loading time and needs no modification of the application~\citep{otelJavaAgent}. This zero-code property is the decisive fairness argument. The connectors under test are heterogeneous: Jetty/Jersey-based \gls{edc} runtimes and a Spring Boot application. The same agent nevertheless instruments all of them, and the \gls{otel} semantic conventions guarantee that the resulting series carry the same names and semantics everywhere. Examples are \texttt{http\_server\_request\_duration} for server-side request latency and the \texttt{jvm\_*} series for heap, \gls{gc}, and thread telemetry~\citep{opentelemetrySemconv}. Each container sets a distinct \texttt{OTEL\_SERVICE\_NAME}, so every runtime is separable in every downstream query, and the agent exports over OTLP/gRPC every 5\,s.

\textbf{Collection and storage.} All agents push to a single \gls{otel} Collector, which batches the streams and re-exposes the metrics in Prometheus format, converting the \gls{otel} resource attributes into Prometheus labels so that per-runtime attribution survives the format boundary. Prometheus scrapes the collector and the node exporter every 5\,s, matching the agent export interval so that every scrape observes fresh samples. Retention covers one working week, which comfortably outlives the longest scenario and leaves the archived per-run snapshot, not the live database, as the artefact of record.

\textbf{Reading instrument.} Grafana provisions two dashboards from the repository: a rate-error-duration dashboard over the connector \gls{api} series and a host dashboard over the node-exporter series~\citep{grafanaDocs}. Grafana's role is deliberately limited to live inspection -- verifying during a run that the stack is healthy and that load arrives where expected. The measurement of record is never a dashboard screenshot: it is the k6 summary and the Prometheus snapshot CSVs archived per run (\cref{subsec:orchestration}). Both read the same Prometheus instance over the same measured window, and the archival queries reuse the dashboard expressions, so figures and tables in \cref{chap:results-evaluation} describe the same observations. They are not, however, arithmetically interchangeable: a dashboard panel computes rates over Grafana's display-dependent interval, whereas the archival range queries fix that window at one minute, so a rate read off a figure and the corresponding tabulated value differ slightly in smoothing. Where the two are shown together, the table is the citable figure and the image is the illustration.

\subsection{Distributed Tracing}\label{subsec:tracing}

The same agent that produces metrics also emits spans for every instrumented operation, which the collector forwards to Grafana Tempo, a tracing backend running here as a single binary with local storage and a retention of one week~\citep{grafanaTempoDocs}. Traces serve one purpose in this benchmark: decomposing the wall time of a \gls{dsp} transaction into its per-hop constituents -- consumer control plane, provider control plane, data plane -- which is the primary evidence feeding the architectural interpretation of \cref{sec:x1-overhead}. Trace data is queried through Grafana and consulted in the analysis, not gated upon during runs. Instrumentation is never free; the monitoring overhead is itself examined by comparing agent-on and agent-off runs, and the result is reported with the threats to validity in \cref{chap:results-evaluation}.

\subsection{Host-Level Metrics}\label{subsec:host-metrics}

The Prometheus node exporter publishes hardware and operating-system metrics of the benchmark host, of which the analysis uses CPU-busy time and available memory~\citep{prometheusNodeExporter}. Its role follows from the single-host design: when a latency knee appears in a saturation sweep, the host series decide whether the ceiling belongs to the connector or to the machine (\cref{subsec:hardware}). The stack deliberately omits a per-container metrics agent such as cAdvisor: the per-process resource view required by $G_k.\text{RQ}3$ -- heap occupancy, \gls{gc} pause rate, thread count -- is already delivered per runtime by the \gls{otel} agent's \gls{jvm} telemetry, and the host exporter bounds the total. Per run, ten server-side series are archived as CSV files: per-service heap, \gls{gc} rate, and thread count; per-service request throughput, 95th-percentile server latency, combined error rate, server-fault (5xx) rate, and a breakdown by response status code; and host CPU-busy and memory-used. The error rate is archived both combined and split because a merged series cannot distinguish a client-side rejection from a connector fault, and only the latter is a finding about the system under test.


\section{Workload Generation}\label{sec:workload-gen}

\subsection{k6 Harness Architecture}\label{subsec:k6-harness}

Load is generated with Grafana k6, a scriptable load generator whose scenarios are JavaScript programs executed by configurable executors~\citep{k6docs}. Three properties motivated the choice. First, k6 provides open-model arrival-rate executors that fire requests on a clock, independently of how quickly the system responds. A closed loop, in which each virtual user waits for its previous transaction, lets a slow system throttle its own offered load and so hide the latency tail. This is the classic open-versus-closed distortion~\citep{schroeder2006open}. Second, a \gls{dsp} transaction is not a single request but a multi-step, partially asynchronous protocol flow. A k6 script expresses that full sequence as one measured transaction: catalog request, negotiation initiation, polling to the agreed state, transfer initiation, polling to the \gls{edr}, and data pull. Third, custom metrics, tags, and thresholds allow the harness to emit exactly the metric set defined in \cref{sec:metrics} and to enforce per-scenario validity gates.

The harness is maintained as a small software project rather than as a set of ad-hoc scripts, so that running an experiment is one reproducible command instead of a remembered procedure. \Cref{lst:harness-layout} shows its layout: a library layer carrying the protocol flow, the polling logic, the seeding helpers and the metric definitions; the eight scenario scripts; the orchestration and tooling scripts; and one configuration file per connector.

{\pagebreak}

\begin{lstlisting}[numbers=none, basicstyle=\scriptsize\ttfamily, columns=fixed, caption={Layout of the k6 harness. The lib/ and scenarios/ directories are byte-identical in all three connector repositories and are checked as such before every run.}, label=lst:harness-layout]
k6-scripts/
  lib/               protocol flow, HTTP helpers, polling, seeding, metrics
  scenarios/         the eight load shapes
  config/            <connector>.json - the only per-connector file
  orchestration/     run.sh, run-matrix.sh, benchmark-{on,off}.sh,

  tools/             verify-parity.sh, gen-payloads.sh

\end{lstlisting}

The per-connector configuration is the only file that differs between repositories; it holds the management and \gls{dsp} endpoints, the participant identifiers, the seed asset, and the Prometheus address. Everything above it is a byte-identical copy, and a parity checker (\texttt{tools/verify-parity.sh}) diffs \texttt{lib/} and \texttt{scenarios/} against the canonical copy and refuses a run on any drift -- without that guard the duplicated load driver could itself become a confound. One driver therefore exercises six deployments -- three connectors, each in two arms -- selected only by the target configuration and the identity-mode setting. The single exception is the BaSyx $G_2$ arm, whose raw-\gls{dsp} driver variant replaces the \gls{edc} management flow for the reasons given in \cref{subsec:mock-arm}, reproducing the same load shapes and metric definitions against the \gls{dsp} endpoints directly.

\subsection{Deployment and Execution Workflow}\label{subsec:workflow}

Each connector repository exposes the same two entry points next to its Compose files, so that the operating procedure is identical whichever connector is under test. \texttt{install.sh} takes the identity arm as its only argument, selects the matching Compose file, and brings the stack up with monitoring. \texttt{cleanup.sh} tears it down together with its volumes, so that the next run starts from an empty database and not from inherited state. Given no argument, it removes both arms. The three stacks share container names by design and run one at a time on the same host (\cref{subsec:hardware}). \texttt{install.sh} therefore performs a pre-flight check. It removes containers left behind by a previously benchmarked connector, and refuses to start while another connector's stack is still running. A silent cross-connector collision thus becomes an explicit error.

The identity-enabled arms of Factory-X and BaSyx boot with empty Identity Hubs and must be provisioned once before any transaction can succeed -- registering the trusted issuer, creating both participants, requesting their membership credentials, and writing the \gls{sts} client secrets to Vault. That provisioning exists only as an interactive \gls{api} collection, which is unusable on a headless server, so this work ports it to a one-shot k6 script requiring nothing beyond the k6 binary the scenarios already need. The Fraunhofer ISST arm instead ships pre-signed credentials alongside its static \gls{did} documents and needs no such step. \Cref{lst:run-workflow} shows the resulting lifecycle.

\begin{lstlisting}[numbers=none, basicstyle=\scriptsize\ttfamily, columns=fixed, caption={Lifecycle of one benchmark arm, from deployment to teardown.}, label=lst:run-workflow]
# 1  bring up one arm of one connector (stack + monitoring)
./install.sh on                  # identity-enabled arm  (G1)
./install.sh off                 # identity-disabled arm (G2)

# 2  provision the dataspace once - identity-enabled arm only
cd k6-scripts && k6 run identity-setup.js

# 3  run one scenario: connector, arm and scenario are the only variables
IDENTITY_MODE=on ./orchestration/run.sh factoryx steady
RATE=10 DURATION=5m IDENTITY_MODE=on ./orchestration/run.sh factoryx steady

# 4  or the complete arm, unattended: every scenario in the fixed order,
#    with the repeated scenarios repeated and the figures exported
./orchestration/benchmark-on.sh factoryx      # identity-enabled arm  (G1)
./orchestration/benchmark-off.sh factoryx     # identity-disabled arm (G2)

# 5  tear the arm down, volumes included
./cleanup.sh
\end{lstlisting}

Three variables therefore determine any measurement -- the connector, the identity arm, and the scenario -- and each appears exactly once on the command line. The orchestration script wraps the k6 invocation in the measurement pipeline and the archiving described in \cref{subsec:orchestration}. A scenario's load parameters are environment overrides on the same command: offered rate, duration, payload or catalog size, and poll interval. Any deviation from the defaults of \cref{tab:k6-scenarios} is therefore explicit at the call site, and the run's provenance file records it. A Makefile exposes the same targets under shorter names for interactive use, and a payload generator produces the sized files that the data-plane sweep serves.

\texttt{smoke} \textbf{-- correctness gate and uncontended baseline.} A single user runs the full flow five times, and any failure fails the run outright, since without contention a failure indicates a broken stack rather than overload. Run against the $G_2$ arm it doubles as a parity probe: the transaction must succeed \emph{without} a valid credential, confirming that identity is genuinely bypassed.

\texttt{steady} \textbf{-- the realistic operating point.} A fixed offered rate is held below the saturation point of every arm, which makes this the head-to-head comparison point for latency percentiles. The rate is a controlled variable and is identical across connectors: a per-connector rate would compare different experiments rather than different connectors. It is set from the saturation ladders of a preceding campaign, which locate the slowest arm's knee. A rate above any arm's knee censors that arm's latency percentiles at the poll deadline, and would compare one connector in overload against others in steady state. Its open-model executor keeps the tail honest under the coordinated-omission argument of \cref{subsec:k6-harness}~\citep{schroeder2006open}. Sustained capacity is read from \texttt{saturation-open} instead, because at a healthy operating point every connector simply returns the offered rate.

\texttt{poll-sensitivity} \textbf{-- the observer-effect control.} The harness observes the asynchronous state machines by polling, and that polling is itself load on the system under test. In the first campaign, roughly 60\,\% of the requests each connector served at the operating point were the harness's own status polls. This scenario repeats \texttt{steady} unchanged at two poll intervals, so the interval is the only variable, and reports what moves as a result. It answers no research question. It bounds the confidence with which the others may be answered, and \cref{sec:results-validity} reports it with the threats to validity.

\texttt{saturation-open} \textbf{-- the scalability knee.} The offered rate is swept upward in stages to trace the full latency-versus-load curve. Its thresholds are abort-only guards, so the saturation knee and the onset of failure are read from the curve rather than from a pass/fail gate, consistent with the capacity relationship expressed by Little's law~\citep{little1961proof}.

\texttt{concurrency-closed} \textbf{-- the concurrency companion.} Concurrent virtual users are ramped instead of the arrival rate. This maps directly onto the intuitive question of how a connector behaves as more clients transfer at once. As a closed model it is subject to coordinated omission, so it is reported only alongside the open-model result, never as the sole scalability claim.

\texttt{payload-sweep} \textbf{-- data-plane throughput in isolation.} One contract is negotiated during setup, after which only the payload size varies. This isolates raw data-plane throughput from the control-plane handshake, following the one-factor-at-a-time principle of workload construction~\citep{kistowski2015benchmark}. Because identity work concentrates in the control plane, the expected identity overhead here is near zero, which makes this scenario the empirical check on the Factory-X data-plane caveat of \cref{subsec:mock-arm}.

\texttt{soak} \textbf{-- endurance and resource drift.} A gentle rate is applied for thirty minutes to expose heap drift, \gls{gc} degradation, and thread growth that short runs cannot reveal, observed through the \gls{jvm} series~\citep{gregg2012thinking}. The window bounds what may be claimed from it. A trend fitted over half an hour can show that no component is growing fast enough to exhaust the heap on that timescale, but it cannot exclude a slow leak. \Cref{sec:conclusion-limitations} reports it on those terms.

\texttt{catalog-sweep} \textbf{-- control-plane scaling.} The provider is seeded with a controlled number of assets and each iteration issues a catalog-only request. Each of the four sizes is measured twice, since the scenario produces a curve and a single run per size would leave no way to separate a scaling effect from run-to-run noise. Seeding requires the management \gls{api} backed by SQL persistence, so this scenario targets the two \gls{edc} providers; BaSyx catalog scaling is treated separately.

Scenario thresholds play two distinct roles. Gate thresholds (on \texttt{smoke}, \texttt{steady}, \texttt{soak}, and the sweeps) invalidate a run that violates them -- for example, a transaction-failure rate above 1\,\% in \texttt{steady} -- ensuring latency statistics are only reported over essentially successful runs. Abort-only thresholds (on the two ramping scenarios) merely stop a run that has degenerated far past its knee; they are diagnostic bounds, not claims.

The two \texttt{time\_to\_*} trends realise the asynchronous-cycle measurement of \cref{subsec:primary-metrics}. Negotiation and transfer are asynchronous state machines: the client posts a request, receives a non-terminal state, and polls until the terminal state is reached~\citep{eclipseEdcDocumentation}. The harness polls at a fixed interval, 250\,ms by default and recorded with every run, without backoff. The quantisation of the measured wait is therefore uniform: each \texttt{time\_to\_*} value is an upper bound that overstates the true time by at most one poll interval. Every poll is also a real request against the control plane. The harness therefore counts polls per phase instead of hiding this observer effect, and the counts accompany the latency figures in \cref{chap:results-evaluation}. For BaSyx, whose transfer is synchronous by architecture (\cref{sec:sut}), the \gls{edr} wait terminates on the first poll. \texttt{time\_to\_edr} is therefore a real distribution only for the \gls{edc}-based connectors, and the asymmetry itself becomes input to the architectural interpretation.

\subsection{Run Orchestration and Measurement Window}\label{subsec:orchestration}

A single orchestration script executes one experiment -- one connector, one scenario, one arm -- as a fixed pipeline: parity check, health gate, warm-up, measured run, post-roll, server-side snapshot, provenance record. The health gate polls the consumer management \gls{api} and the Prometheus readiness endpoint before anything is measured, so a partially booted stack cannot silently produce degenerate numbers. The warm-up drives 60\,s of light load and is then discarded, letting \gls{jvm} just-in-time compilation and cold caches settle outside the measured window. Omitting it is one of the named common mistakes this design avoids~\citep{jain1991art}. After the measured run, a 15\,s post-roll guarantees that the final 5\,s scrape falls inside the observation window. The script then executes the range queries of \cref{subsec:host-metrics} over exactly the run's start and end epochs, and archives the server view time-aligned with the client view.

Every run terminates in an immutable result folder. Its provenance file records every parameter needed to reproduce or audit that run: connector, scenario, arm, poll interval, catalog size, start and end epochs, the k6 version and exit code, the load knobs, and the git commit of the harness.

\begin{lstlisting}[numbers=none, basicstyle=\scriptsize\ttfamily, columns=fixed, caption={Per-run result folder produced by the orchestration script.}, label=lst:result-folder]
results/<connector>/<arm>/<scenario>/<UTC-timestamp>/
  run.log          k6 console output of the measured run
  k6-summary.json  client-side metrics (p50/p95/p99 per trend)
  *.csv            ten server-side series from Prometheus
  logs/            per-container logs for the measured window
  meta.json        parameters, epochs, identity mode, git commit
\end{lstlisting}

A campaign script layers the repetition discipline on top and drives a complete arm unattended. The sequence, the spacing between scenarios, and the environment are therefore fixed across all six connector--arm combinations, instead of varying with the session that executed them. Repetition is allocated where it is informative, in proportion to how much a result depends on the scenario, and not spread uniformly. \texttt{steady} is executed five times, because it carries both the head-to-head operating-point comparison and every identity-overhead figure, and because five is the smallest count from which an interval estimate is defensible at all. \texttt{saturation-open} is executed three times, since the saturation point is a headline result and a single run offers no way to tell a difference between connectors from run-to-run variation. \texttt{catalog-sweep} is executed twice at each size, so that the shape of the scaling curve is not decided by one observation per point. The remainder run once, and their construction justifies it. \texttt{smoke} is a pass/fail gate, not a measurement. \texttt{payload-sweep} varies a factor across five sizes instead of repeating one condition. \texttt{soak} is itself a thirty-minute observation window from which a trend is fitted, and \texttt{concurrency-closed} traverses a ladder whose rungs corroborate one another.

The repetition counts bound what may be claimed. Five values support a range and a stated resolution. Two support neither an interquartile range nor a variability claim, which is why the sweeps are reported as curves and not as points with error bars. Spread is reported as the observed range and as the relative range defined in \cref{subsec:analysis-statistics}, and a difference smaller than that range is reported but not interpreted.

The scenario order within an arm is fixed rather than randomised, which forgoes the mitigation of ordering bias in exchange for removing a larger confound~\citep{jain1991art}. The scenarios are not independent of one another: the catalog sweep leaves up to a thousand assets in the provider, and the ramped scenarios overload the connector by design and leave transfers draining behind them. Under a randomised order a scenario's result would depend on which scenario happened to precede it in that particular arm, and the arms would no longer be comparable -- the condition on which the entire identity contrast rests. The fixed sequence therefore runs the undisturbed scenarios first, places the data-plane sweep ahead of the catalog sweep that would otherwise pollute it, and defers the overloading ramps to the end. A settling interval separates every scenario, and each run records the age of the stack it executed against (\cref{subsec:orchestration}), so that any residual order effect remains detectable after the fact rather than being assumed absent.

Connector deployments are never run in parallel (\cref{subsec:hardware}). The complete matrix is three connectors $\times$ two arms $\times$ eight scenarios, executed one connector--arm at a time. Expanded over the sweep sizes, the repeated scenarios, and the two poll intervals of the observer-effect control, one identity arm of an \gls{edc}-based connector comprises twenty-six measured runs. One arm of BaSyx comprises thirteen, since neither the catalog nor the payload sweep applies to it (\cref{subsec:parity}). Repetitions are aggregated to medians, with the spread reported as the observed range, before any figure in \cref{chap:results-evaluation} is drawn~\citep{jain1991art, hoefler2015scientific}.


\section{Data Analysis}\label{sec:data-analysis}

The preceding sections describe how measurements are produced and archived. This one describes how they are reduced to the answers of \cref{chap:results-evaluation}. A single program performs that reduction: it reads the immutable result folders of \cref{lst:result-folder} and emits one table per results table. It uses the Python standard library only, so that the analysis can be re-executed without an environment and read without one. The program contains one function per table in \cref{chap:results-evaluation}, each named after that table's cross-reference label and writing a comma-separated file of the same name. No number reported in this thesis originates anywhere else. The same functions run against every connector and both arms with no per-connector special-casing, which keeps the cross-connector comparison a comparison of connectors and not of analyses~\citep{kistowski2015benchmark}.

Three sources feed it, and they are deliberately not interchangeable. The k6 summary carries the client's view of every measured window, aggregated per metric. The Prometheus snapshots carry the server's view of the same window, sampled every five seconds. The k6 console log carries the only time-resolved client record. k6 summarises a whole run as one set of statistics, so a ramped scenario cannot be read from the summary at all. The console, by contrast, prints a cumulative completed-iteration count once per second, and differencing that recovers what each load rung actually delivered. Because the client and the server observe the same window through independent instruments, their agreement corroborates a figure and their disagreement is itself a finding~\citep{hasselbring2021benchmarking}.

\subsection{Statistical Treatment}\label{subsec:analysis-statistics}

The unit of replication is the \emph{run}, not the transaction. Two runs of one arm share a host, a \gls{jvm} just-in-time state, a database, and a connection pool, so the several hundred transactions inside a single run are not independent observations of the connector~\citep{jain1991art, hoefler2015scientific}. Counting them as independent would inflate the sample size by three orders of magnitude and claim a precision the design does not have. Every reported figure is therefore computed across runs, each run contributing the single value that summarises it, and the number of repetitions accompanies every result.

Four statistics are computed and no others. \Cref{tab:analysis-statistics} gives each one with the reason it is chosen; the remainder of the analysis is reading values out of the archived files.

    \centering

No significance test accompanies any comparison. A $p$-value or a confidence interval requires enough independent replicates to estimate variability, and at two runs per arm any such figure would be produced by the assumption used to compute it rather than by the data~\citep{hoefler2015scientific}. The range takes its place: where the two arms' observed ranges do not overlap, the difference between them exceeds the run-to-run variation of the arms themselves; where they overlap, the comparison is reported as inconclusive rather than as a small effect. This is a weak criterion and is labelled as one wherever it is used.

Two quantities are not read directly from a summary. The delivered rate of each rung in the ramped scenarios is obtained by differencing the load generator's cumulative iteration count over that stage, because the per-run summary averages every rung into every other. That rate is then compared against the mean rate offered during the stage, not against its nominal target. The generator ramps linearly towards the target, so the target is the rate reached at the end of a rung and not the rate offered across it. Comparing against it understates delivery on every ramped rung~\citep{k6docs}. Catalog scaling is expressed as two growth factors, one for the catalog and one for the request latency, in preference to a fitted exponent. The plain statement answers $G_k.\text{RQ}5$ without asking the reader to interpret a log--log slope.

\subsection{Which Runs Are Used}\label{subsec:runs-used}

Not every run measures what it is meant to measure. A rule is therefore fixed in advance and applied to every connector and both arms alike, so that the decision to trust a run never depends on what that run happened to show. The rule is implemented in one place, which is what stops the audit and the results tables from disagreeing about it.

A run is discounted if any of three conditions holds:

\begin{enumerate}[leftmargin=*, itemsep=2pt, topsep=4pt]
    \item \textbf{The load generator does not deliver the offered load.} Some iterations never start, so the run describes the driver rather than the connector.
    \item \textbf{More than five per cent of transactions missed the poll deadline.} The run then sat beyond its saturation point. A transaction abandoned at the deadline contributes the deadline to the statistics rather than the time it would really have taken, so the latency percentiles of such a run are lower bounds and not measurements.
    \item \textbf{No transaction completed.} There is nothing to interpret.
\end{enumerate}

The two ramped scenarios are exempt from the first two conditions at their highest rungs, since reaching those conditions is what they exist to do (\cref{subsec:scenarios}).

A discounted run is marked rather than deleted. Where it is the only observation available for a cell, deleting it would hide the very thing it shows. A connector that cannot sustain the operating point produces exactly this pattern, and an empty cell would present that as missing data instead of as a result. Every run and its verdict therefore appears in the audit table of \cref{chap:results-evaluation}, and every results table drawing on a marked run repeats the caveat. Reporting anomalous observations instead of removing them quietly is the expectation set by the empirical standard for benchmarking studies~\citep{Ralph2020}.

\section{Reproducibility}\label{sec:reproducibility}

The benchmarking standard requires documentation sufficient for replication~\citep{Ralph2020, empiricalStandardsBenchmarking}; this setup meets the requirement by making the repositories themselves the documentation. Everything an experiment consumes is version-controlled on one branch (\texttt{feat/final-setup}) of each connector repository: the Compose files of both arms, the monitoring configuration and dashboards, the mock-identity extension and assemblies, the k6 harness with all scenario parameters, and the orchestration scripts. Third-party images are pinned by tag (\cref{subsec:substrate}); first-party images are built from the repository, and the commit hash recorded in every run's provenance file ties each result to the exact source state that produced it. Each reported figure is therefore traceable to one or more immutable result folders, and every X1 value to the two paired folders it is differenced from.

Replicating a connector's measurement reduces to five steps on a comparable Docker host:

\begin{enumerate}[leftmargin=*, itemsep=1pt, topsep=4pt]
    \item clone the connector repository at the audited branch;
    \item build the first-party images;
    \item start the desired arm with its Compose file;
    \item for an identity-enabled arm, run the one-shot identity provisioning;
    \item invoke the campaign script for that arm.
\end{enumerate}
 \Cref{sec:test-env} specifies the environment that produced the reported numbers. The principles this procedure follows are the established ones for reproducible performance evaluation: a controlled environment, repeated runs, and distribution-based reporting~\citep{papadopoulos2021reproducible, hoefler2015scientific}. Residual nondeterminism remains. A shared physical host, \gls{jvm} just-in-time variability, and network jitter inside the container network are not eliminated. The discarded warm-up, the settling interval between scenarios, and median-based reporting mitigate them, and the host-level series of \cref{subsec:host-metrics} quantify them instead of assuming them away. The scenario order is fixed, not randomised, for the reason given in \cref{subsec:orchestration}. Ordering effects are therefore not averaged out across arms; they are made auditable instead. The stack age recorded with every run allows a suspected carry-over to be tested against the data rather than argued about. The known deviations from full uniformity -- the untagged base images in one repository, the host-versus-bridge networking difference, and the BaSyx driver asymmetry -- are stated in \cref{sec:deployment,subsec:substrate} and revisited as threats to validity in \cref{chap:results-evaluation}.
